# Тестирование проекта

Этот документ описывает тестовую структуру проекта `C# Quest`, назначение автоматических тестов, текущее покрытие по сценам и практический порядок запуска тестов в Unity.

Документ можно использовать как:
- внутреннюю памятку по тестам;
- основу для раздела диплома о верификации и проверке качества;
- краткую карту для следующего разработчика или ИИ-ассистента.

## Назначение тестов

Автоматические тесты в проекте используются для проверки двух разных уровней поведения:

- `EditMode` тесты проверяют изолированную логику скриптов без запуска полноценной игровой сцены;
- `PlayMode` тесты проверяют, что сцена действительно загружается, а ключевые runtime-компоненты уровня присутствуют и поднимаются в рабочем контексте Unity.

Такой подход выбран потому, что проект сочетает:
- чистую игровую логику;
- сценозависимые `MonoBehaviour`;
- сериализованные ссылки;
- runtime-поведение, завязанное на Unity Scene system, UI и игровые объекты.

Из-за этого одна часть функциональности удобнее и надёжнее проверяется в `EditMode`, а другая только в `PlayMode`.

## Структура тестов

Тесты расположены в папке `Assets/Tests` и разделены на два набора:

- `Assets/Tests/EditMode`
- `Assets/Tests/PlayMode`

Для Unity Test Runner используются отдельные test assembly definition:

- `Assets/Tests/EditMode/OKEI.EditModeTests.asmdef`
- `Assets/Tests/PlayMode/OKEI.PlayModeTests.asmdef`

Дополнительно используются вспомогательные файлы:

- `Assets/Tests/EditMode/TestHelpers/TestReflectionUtility.cs`
- `Assets/Tests/EditMode/TestHelpers/TestSaveFileUtility.cs`
- `Assets/Tests/EditMode/TestHelpers/AssemblyTypeUtility.cs`
- `Assets/Tests/PlayMode/TestHelpers/SceneTestUtility.cs`
- `Assets/Tests/PlayMode/TestHelpers/AssemblyTypeUtility.cs`

### Почему в тестах используется reflection

Основная игровая логика проекта находится в стандартной сборке `Assembly-CSharp`. В тестовых сборках Unity не всегда удобно или стабильно делать прямые compile-time ссылки на эти классы, особенно в проектах без собственной доменной модульной разбивки на runtime `asmdef`.

Поэтому часть тестов получает типы через reflection:
- это уменьшает количество конфликтов сборки;
- позволяет обращаться к runtime-классам сцены без реорганизации всего проекта;
- сохраняет тесты независимыми от внутренней схемы Unity-сборок.

## Принцип покрытия

Для каждой из 5 основных сцен проекта сделано по 2 теста:

- 1 `EditMode` тест;
- 1 `PlayMode` тест.

Итог:
- `5 EditMode` тестов;
- `5 PlayMode` тестов;
- `10` пользовательских тестов всего.

## Покрытие по сценам

Ниже перечислено, что именно проверяется для каждой сцены.

### 1. Bootstrap

#### EditMode

Файл:
- `Assets/Tests/EditMode/Bootstrap/BootstrapEditModeTests.cs`

Проверяемое поведение:
- завершение уровня корректно отмечает уровень как пройденный;
- сохраняется факт прохождения;
- разблокируется следующий уровень;
- обновляется индекс последнего сыгранного уровня.

Что именно валидируется:
- `CompleteLevel(1)` добавляет уровень в список завершённых;
- `GetMaxUnlockedLevel()` становится равным `2`;
- `GetLastPlayedLevel()` становится равным `1`.

#### PlayMode

Файл:
- `Assets/Tests/PlayMode/Bootstrap/BootstrapPlayModeTests.cs`

Проверяемое поведение:
- сцена `Bootstrap` успешно загружается;
- на сцене присутствует `LevelProgressManager`;
- у менеджера есть сконфигурированный список уровней.

Что именно валидируется:
- количество уровней в `LevelProgressManager` не меньше `4`.

Практический смысл:
- тест подтверждает, что bootstrap-сцена не потеряла основной runtime-объект управления прогрессом и выбором уровней.

### 2. Level1

#### EditMode

Файл:
- `Assets/Tests/EditMode/Level1/Level1EditModeTests.cs`

Проверяемое поведение:
- система условий двери корректно вычисляет необходимое количество слотов на основе выражения условия.

Что именно валидируется:
- если в выражении встречается условие со `SlotIndex = 2`, система должна потребовать минимум `3` слота.

Практический смысл:
- это проверяет базовую логику учебной механики уровня с условиями и значениями.

#### PlayMode

Файл:
- `Assets/Tests/PlayMode/Level1/Level1PlayModeTests.cs`

Проверяемое поведение:
- сцена `Level1` загружается;
- на сцене присутствует `DoorCondition`;
- на сцене присутствует `FinalPortal`.

Практический смысл:
- тест подтверждает, что ключевая механика условий и объект завершения уровня существуют в реальной сцене.

### 3. Level2

#### EditMode

Файл:
- `Assets/Tests/EditMode/Level2/Level2EditModeTests.cs`

Проверяемое поведение:
- `LockInputs` корректно восстанавливает внутреннее состояние переключателей;
- флаг доступности ввода корректно обновляется.

Что именно валидируется:
- после `RestoreState(false, false, false, false)` все параметры выключены;
- после включения флага ввода и восстановления состояния в `true` все параметры становятся включёнными.

Почему тест не вызывает реальные toggle-методы:
- переключатели уровня 2 используют аудио-runtime, который в `EditMode` приводит к вызовам `DontDestroyOnLoad`;
- поэтому в изолированном тесте проверяется логика состояния, а не побочный runtime-эффект аудио.

#### PlayMode

Файл:
- `Assets/Tests/PlayMode/Level2/Level2PlayModeTests.cs`

Проверяемое поведение:
- сцена `Level2` загружается;
- на сцене присутствует `LockControlSystem`;
- на сцене присутствует `LockInputs`;
- у системы есть валидный `SaveId`.

Практический смысл:
- тест подтверждает, что центральная механика шлюза и циклов действительно поднята в рабочем runtime-контексте.

### 4. Level3

#### EditMode

Файл:
- `Assets/Tests/EditMode/Level3/Level3EditModeTests.cs`

Проверяемое поведение:
- `Level3ArtifactManager` корректно считает собранные артефакты;
- после обработки всех артефактов отмечается открытие финальной двери.

Что именно валидируется:
- после регистрации первого артефакта счётчик равен `1`;
- после регистрации второго артефакта счётчик равен `2`;
- внутренний флаг `_finalDoorOpened` становится `true`.

Почему используется `NotifyArtifactRestored`, а не обычный pickup-метод:
- обычный путь подбора артефакта запускает аудио-runtime;
- в `EditMode` это даёт лишние побочные эффекты;
- для проверки логики менеджера достаточно безопасного пути без звука.

#### PlayMode

Файл:
- `Assets/Tests/PlayMode/Level3/Level3PlayModeTests.cs`

Проверяемое поведение:
- сцена `Level3` загружается;
- на сцене присутствует `Level3ArtifactManager`;
- в сцене зарегистрирован хотя бы один артефакт;
- присутствует `FinalDoorController`.

Практический смысл:
- тест подтверждает, что уровень с артефактами содержит базовую цепочку прохождения: менеджер, артефакты и финальную дверь.

### 5. Level4

#### EditMode

Файл:
- `Assets/Tests/EditMode/Level4/Level4EditModeTests.cs`

Проверяемое поведение:
- `Level4ProgressModule` корректно определяет доступность режима отряда после разблокировки всех специальных типов роботов.

Что именно валидируется:
- если разблокированы `Base`, `Attacker`, `Healer`, `Defender`, то `IsSquadModeUnlocked(...)` возвращает `true`.

Практический смысл:
- этот тест покрывает важную часть логики прогрессии уровня с наследованием и роботами.

#### PlayMode

Файл:
- `Assets/Tests/PlayMode/Level4/Level4PlayModeTests.cs`

Проверяемое поведение:
- сцена `Level4` загружается;
- на сцене присутствует `Level4FlowController`;
- на сцене присутствует `RobotUnlockManager`;
- на сцене присутствует `RobotSelectionUI`.

Особенность текущей реализации:
- поиск `RobotSelectionUI` выполняется не только среди активных объектов;
- если UI-компонент существует в сцене, но временно выключен на старте, тест всё равно сможет его найти как сценовый объект.

Практический смысл:
- тест подтверждает, что основной orchestration-слой уровня с роботами реально присутствует в игровой сцене.

## Что именно доказывают эти тесты

Текущий набор тестов не пытается покрыть весь проект целиком. Вместо этого он решает более практическую задачу:

- проверяет, что каждая ключевая сцена имеет минимум одну автоматическую проверку логики и одну автоматическую проверку runtime-сборки сцены;
- фиксирует базовые инварианты прохождения;
- помогает быстро замечать регрессии после изменений в сценах, префабах и скриптах.

Иными словами, тесты выполняют роль:
- smoke-проверок сцен;
- базовых логических unit-like тестов;
- минимального барьера от поломки учебных механик.

## Ограничения текущего подхода

У текущего набора тестов есть осознанные ограничения.

### 1. Не все механики можно безопасно тестировать в EditMode

Часть скриптов вызывает:
- `GameAudio`;
- `DontDestroyOnLoad`;
- scene transition runtime;
- автосохранение;
- другие PlayMode-специфичные эффекты.

Поэтому в `EditMode` проверяется не весь пользовательский сценарий, а логическое ядро без побочных runtime-эффектов.

### 2. PlayMode тесты сейчас ближе к smoke/integration, чем к полному e2e

Они подтверждают:
- загрузку сцены;
- наличие ключевых компонентов;
- базовую валидность runtime-структуры.

Но они пока не симулируют весь путь игрока:
- взаимодействие с дверями;
- полный цикл прохождения Level2;
- физический сбор всех артефактов;
- реальный бой роботов на Level4.

### 3. Reflection делает тесты гибкими, но менее строгими по типизации

Плюсы:
- меньше проблем со сборкой Unity;
- проще подключить тесты к существующему проекту.

Минусы:
- ошибки части API всплывают не на compile-time, а во время выполнения теста;
- тесты чуть сложнее читать, чем прямые strongly-typed unit tests.

## Как запускать тесты

### В Unity Editor

1. Открыть `Window -> General -> Test Runner`.
2. Перейти во вкладку `EditMode`.
3. Нажать `Run All`.
4. После завершения перейти во вкладку `PlayMode`.
5. Нажать `Run All`.

### Через batchmode

Запуск возможен только если проект не открыт в другом Unity-инстансе.

#### EditMode

```powershell
& 'D:\UnityHub\Editor\Editor\Unity.exe' `
  -batchmode -nographics `
  -projectPath 'D:\GitRepos\OKEI' `
  -runTests `
  -testPlatform EditMode `
  -logFile 'D:\GitRepos\OKEI\Temp\editmode-tests.log' `
  -testResults 'D:\GitRepos\OKEI\Temp\editmode-results.xml'
```

#### PlayMode

```powershell
& 'D:\UnityHub\Editor\Editor\Unity.exe' `
  -batchmode -nographics `
  -projectPath 'D:\GitRepos\OKEI' `
  -runTests `
  -testPlatform PlayMode `
  -logFile 'D:\GitRepos\OKEI\Temp\playmode-tests.log' `
  -testResults 'D:\GitRepos\OKEI\Temp\playmode-results.xml'
```

## Как читать результаты

Если падает `EditMode` тест, чаще всего это означает одно из трёх:

- нарушена внутренняя логика скрипта;
- изменились приватные поля или методы, на которые опирается reflection;
- тест задел runtime-поведение, которое нельзя вызывать вне `PlayMode`.

Если падает `PlayMode` тест, чаще всего это означает:

- сцена потеряла важный объект;
- сериализованные ссылки больше не настроены корректно;
- во время загрузки сцены произошла runtime-ошибка;
- изменилось имя сцены или архитектура уровня.

## Практическая ценность для диплома

Этот набор тестов можно описывать в дипломе как минимальную автоматизированную систему контроля качества, ориентированную на учебную игру на Unity.

Корректная формулировка сути:
- в проекте реализована двухуровневая стратегия тестирования;
- логика ключевых подсистем проверяется модульными `EditMode` тестами;
- работоспособность сцен и наличие основных игровых компонентов проверяются `PlayMode` тестами;
- для каждой основной сцены создано по две автоматические проверки: логическая и runtime-проверка сцены.

## Готовые формулировки для дипломного текста

Ниже несколько заготовок, которые можно адаптировать.

### Вариант 1. Кратко

В проекте реализовано автоматизированное тестирование на базе Unity Test Framework. Для каждой из пяти основных сцен игры были подготовлены два теста: `EditMode` тест для проверки логики соответствующей подсистемы и `PlayMode` тест для проверки корректной загрузки сцены и наличия ключевых игровых компонентов. Такой подход позволил обеспечить базовый контроль качества как на уровне программной логики, так и на уровне интеграции скриптов со сценами Unity.

### Вариант 2. Более академично

Для повышения надёжности программной части проекта была внедрена система автоматизированной верификации с использованием Unity Test Framework. Архитектура тестирования разделена на два уровня. На первом уровне применяются `EditMode` тесты, предназначенные для изолированной проверки логики игровых подсистем без запуска полной сцены. На втором уровне используются `PlayMode` тесты, позволяющие проверять корректную загрузку сцен и наличие критически важных runtime-компонентов. Для каждой основной сцены проекта был сформирован отдельный набор из двух тестов, что позволило уменьшить риск регрессий при дальнейшем развитии проекта.

### Вариант 3. С акцентом на практику

В рамках разработки была создана минимальная, но practically useful система автоматических тестов. Она охватывает все основные сцены проекта: главное меню, уровень с условиями, уровень с циклами, уровень со сбором артефактов и уровень с роботами. Для каждой сцены реализован один тест логики и один тест сценового выполнения. Это позволило использовать тесты как инструмент быстрой проверки после изменений в коде и конфигурации сцен.

## Рекомендации по расширению тестов

Если проект будет развиваться дальше, логично расширять покрытие в следующих направлениях:

- добавить проверки `DoorCondition` не только на количество слотов, но и на вычисление самих условий;
- покрыть `Level2` отдельными сценариями переходов фаз;
- добавить тесты сохранения и восстановления прогресса;
- добавить `PlayMode` тесты на завершение уровня через реальные действия игрока;
- покрыть `Level4` отдельными тестами на прогрессию разблокировки роботов;
- добавить отдельную проверку на корректное количество `EventSystem` в сценах с UI.

## Итог

Текущая тестовая система является стартовым, но уже полезным слоем автоматической проверки качества. Она:

- покрывает все 5 основных сцен проекта;
- разделяет проверки логики и сценового runtime;
- помогает обнаруживать регрессии после изменений в коде и сценах;
- подходит как техническая база для описания раздела тестирования в дипломной работе.
